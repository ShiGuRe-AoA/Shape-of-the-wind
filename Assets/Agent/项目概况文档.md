# Bird Flight Simulation Project Overview

## 1. 项目一句话概述

这是一个鸟类飞行模拟游戏原型。

项目的最终目标是使用 VR 设备的手柄拟真操控鸟的双翼，让玩家通过挥动双臂来模拟小鸟拍打翅膀，从而完成飞行、转向、滑翔、借风上升等操作。

当前阶段可以使用普通手柄、键鼠或临时输入脚本进行模拟，但核心系统设计应始终考虑未来替换为 VR 手柄输入。

## 2. 项目体验目标

本项目希望让玩家感受到“自己正在像鸟一样飞行”。

飞行不应只是普通角色控制器的上下左右移动，而应该尽量体现：

```txt id="4fsx7t"
挥动翅膀产生升力
双翼姿态影响转向
翼展影响滑翔和受风能力
风场影响玩家飞行路线和高度
玩家需要借助风，而不是完全无视环境飞行
```

游戏核心体验并不是精密航空模拟，而是一个以物理反馈和风场交互为核心的飞行体验原型。

## 3. 技术环境概况

项目是 Unity 3D 项目。

渲染管线使用 URP。

未来项目将作为 VR 项目，接入 VR 摄像头与 VR 手柄。

当前阶段使用手柄模拟 VR 操作。

项目已允许使用 Cinemachine 作为摄像机控制系统。

项目已允许使用 DOTween 进行简单动画、UI 动效或表现层补间。

## 4. 物理系统基本原则

本项目与物理系统高度相关，会借用 Unity Rigidbody 的基础功能。

允许使用：

```txt id="io92mi"
Rigidbody
Collider
Physics.Raycast
Physics.OverlapSphere
Rigidbody.AddForce
Rigidbody.AddTorque
Rigidbody.velocity
Rigidbody.angularVelocity
```

应谨慎使用或避免使用：

```txt id="hz9rx9"
AddForceAtPosition
偏心力
复杂关节
HingeJoint
ConfigurableJoint
SpringJoint
角色身体各部位物理拼接
复杂布娃娃物理
```

原因是本项目需要保持飞行物理可控、可调、可理解。高级物理功能容易导致系统变得不可预测，不利于快速调参和玩法验证。

如果需要模拟翅膀对鸟身体的影响，优先通过中心点施加力、施加简单扭矩、或修改飞行控制参数来实现，而不是依赖真实翅膀关节物理。

## 5. 飞行控制核心数值

项目高度关心以下三个玩家输入相关数值。

### 5.1 单翼挥动速度

每个翅膀都应记录自己的挥动速度。

```txt id="enpiu1"
向下挥动为正值
向上挥动为负值
静止或接近静止时接近 0
```

该数值主要影响：

```txt id="pw6pu0"
升力大小
体力消耗
拍翼反馈
飞行动作表现
```

通常情况下，向下挥动越快，产生的主动升力越强，同时体力消耗越高。

向上挥动一般不应产生同等升力，可以产生较弱影响，或者主要作为回收动作。

### 5.2 双翼倾角

玩家左右两翼都应记录自己的倾角。

双翼倾角主要用于控制转向、偏航、滚转或飞行姿态。

例如：

```txt id="u7jfja"
左翼和右翼倾角接近时，玩家保持较稳定的前进或滑翔
一侧翼角变化更大时，玩家向对应方向转向
双翼倾角差值越大，转向趋势越明显
```

具体转向公式可以根据手感调整，不需要追求严格空气动力学真实。

### 5.3 翼展

翼展表示玩家双臂展开的程度。

可以理解为一个 0 到 1 的归一化值：

```txt id="u8e0qp"
0 表示双臂收拢
1 表示双臂充分展开
```

翼展主要影响：

```txt id="pssfhh"
风力作用系数
滑翔能力
受风面积
上升气流利用效率
```

翼展越大，玩家越容易受到风的影响，也越适合滑翔和借助上升气流。

翼展越小，玩家受风影响越弱，可能更适合快速俯冲、穿过狭窄区域或降低风干扰。

## 6. VR 操作目标

最终 VR 操作中，应将玩家手柄位置和运动映射为鸟的双翼状态。

推荐抽象关系：

```txt id="mjn1qm"
左手柄 -> 左翼
右手柄 -> 右翼
手柄上下运动速度 -> 翅膀挥动速度
手柄旋转姿态 -> 翅膀倾角
两手柄距离 -> 翼展
```

当前阶段不要求真实接入 VR，但代码设计应避免把输入逻辑写死在普通手柄上。

推荐保留一个输入抽象层，例如：

```txt id="clbsqm"
BirdInputReader
  负责输出左右翼挥动速度、左右翼倾角、翼展等飞行输入数据

GamepadBirdInputProvider
  当前阶段使用普通手柄模拟鸟翼输入

VRBirdInputProvider
  未来使用 VR 手柄真实计算鸟翼输入
```

核心飞行逻辑应读取统一的鸟翼输入数据，而不是直接读取某个具体设备。

## 7. 风系统概况

游戏核心玩法与“风”高度相关。

风不是单一全局常量，而是由 3D 场景中的多个“风力探针”共同描述。

风力探针是场景中的空物体，挂载相关脚本，用于表示某个空间位置附近的风。

每个风力探针至少应包含：

```txt id="1j2wcq"
风向
风力大小
影响半径或权重参数
是否启用
调试显示参数
```

探针本身不直接推动玩家，而是向风场系统登记自己的位置和风数据。对象需要风力时，向风场系统查询当前位置受到的综合风。

## 8. 风力探针空间哈希

场景空间会被划分为若干单元格。

每个单元格使用 `Vector3Int` 作为 key。

风力探针根据自己的世界坐标计算所属单元格，并存储到字典中。

推荐数据结构概念：

```csharp id="b9v3f0"
Dictionary<Vector3Int, List<WindProbe>> windProbeGrid;
```

坐标到单元格的映射应类似：

```csharp id="eznkar"
Vector3Int cell = new Vector3Int(
    Mathf.FloorToInt(worldPos.x / cellSize),
    Mathf.FloorToInt(worldPos.y / cellSize),
    Mathf.FloorToInt(worldPos.z / cellSize)
);
```

`cellSize` 应作为可调参数暴露给 Inspector，方便根据场景规模调整。

风力探针移动时，需要更新自己在空间哈希中的登记位置。如果风力探针大多是静态的，则可以在启动时统一注册，减少运行时维护成本。

## 9. 风力查询逻辑

当一个对象试图获取自身受到的风时，应访问以自身为中心的邻近空间单元格。

在 3D 场景中，默认理解为查询自身所在单元格周围的 `3 x 3 x 3` 单元格范围。

也就是：

```txt id="7hl8x2"
x: 当前 cell.x - 1 到 当前 cell.x + 1
y: 当前 cell.y - 1 到 当前 cell.y + 1
z: 当前 cell.z - 1 到 当前 cell.z + 1
```

遍历这些单元格中的所有风力探针，根据对象与探针的距离计算影响权重，再将所有探针影响加权求和，得到当前位置的综合风。

推荐概念流程：

```txt id="s0lcmn"
1. 根据对象世界坐标计算当前 cell
2. 遍历周围 3 x 3 x 3 个 cell
3. 收集这些 cell 中的 WindProbe
4. 对每个 WindProbe 计算距离权重
5. 将 WindProbe 的方向 * 强度 * 权重 累加
6. 返回最终风向量
```

最终查询结果应优先返回一个 `Vector3 windVector`。

其中：

```txt id="11yex0"
windVector.normalized 表示综合风向
windVector.magnitude 表示综合风力大小
```

## 10. 风力权重建议

风力探针对目标的影响应随距离衰减。

可以使用简单、稳定、容易调参的权重公式。

示例：

```csharp id="xbtjgz"
float distance = Vector3.Distance(targetPosition, probe.Position);
float t = Mathf.Clamp01(1f - distance / probe.Radius);
float weight = t * t;
```

这表示距离越近，影响越强；超过半径后，影响为 0。

也可以先使用更简单的线性衰减：

```csharp id="qewnej"
float weight = Mathf.Clamp01(1f - distance / probe.Radius);
```

临时项目中优先使用简单公式，不要过早引入复杂流体模拟、噪声流场或 Navier-Stokes 等高级方案。

## 11. 玩家受到风时的力

玩家处于风场中时，主要受到两个由风产生的力。

### 11.1 沿风向的推动力

第一个力沿风力方向。

其大小直接与风力大小相关。

概念公式：

```txt id="i64rj3"
windPushForce = windDirection * windStrength * windPushMultiplier
```

该力表现为风把玩家顺着风向推走。

### 11.2 沿双翼中垂线向上的升力

第二个力沿两翼中垂线向上。

其大小由风力大小和翼展共同影响。

概念公式：

```txt id="p7jsee"
windLiftForce = wingUpDirection * windStrength * wingSpan * windLiftMultiplier
```

其中：

```txt id="xdrctd"
wingUpDirection 表示由双翼姿态推导出的上升方向
windStrength 表示当前综合风力大小
wingSpan 表示双臂展开程度
windLiftMultiplier 表示可调倍率
```

该力表现为玩家展开翅膀时，更容易借助风获得上升或滑翔能力。

## 12. 主动拍翼升力

除了风带来的力，玩家主动拍翼也应该产生升力。

左右翼可以分别计算挥动速度，然后合成为整体升力。

推荐概念：

```txt id="4v34g8"
leftFlapSpeed  左翼挥动速度
rightFlapSpeed 右翼挥动速度
averageDownFlapSpeed = max(0, leftFlapSpeed) 与 max(0, rightFlapSpeed) 的平均值
activeLiftForce = birdUpDirection * averageDownFlapSpeed * activeLiftMultiplier
```

只有向下挥动时才主要产生升力。

如果两翼挥动差异较大，可以额外产生转向或姿态变化，但应保持简单可控。

## 13. 体力消耗

玩家挥动翅膀应消耗体力。

体力消耗主要与挥动速度相关。

推荐概念：

```txt id="try25s"
flapStaminaCost = abs(leftFlapSpeed) + abs(rightFlapSpeed)
```

也可以只让向下挥动消耗主要体力：

```txt id="upg3yy"
flapStaminaCost = max(0, leftFlapSpeed) + max(0, rightFlapSpeed)
```

实际选择取决于手感。临时阶段优先实现简单、直观、容易调参的版本。

体力不足时，可以降低主动拍翼升力，但不一定完全禁止受风滑翔。

## 14. 推荐核心脚本职责

推荐以少量清晰脚本组织核心系统。

```txt id="ss7eb1"
BirdInputReader
  输出鸟翼输入数据，例如左右翼挥动速度、左右翼倾角、翼展

BirdFlightController
  根据输入、风力、体力等数据计算玩家 Rigidbody 受到的力

BirdStamina
  管理体力恢复、体力消耗、体力不足状态

WindProbe
  描述单个风力探针的位置、方向、强度、半径

WindFieldManager
  管理风力探针注册、空间哈希、风力查询

WindReceiver
  可选组件，表示一个对象会受到风场影响

BirdDebugDisplay
  可选调试组件，用于显示当前风力、翼展、拍翼速度等关键数值
```

不需要一开始就写复杂框架。优先让风场查询和玩家飞行先跑起来。

## 15. 推荐数据流

推荐核心数据流如下：

```txt id="lrzfk7"
玩家输入设备
  -> BirdInputReader
    -> 输出 BirdWingInputData

WindProbe
  -> 注册到 WindFieldManager
    -> WindFieldManager 维护空间哈希字典

BirdFlightController
  -> 从 BirdInputReader 读取鸟翼输入
  -> 从 WindFieldManager 查询当前位置风力
  -> 计算主动拍翼升力、风推动力、风升力、转向扭矩
  -> 对 Rigidbody 施加力和简单扭矩
```

核心飞行控制应放在 `FixedUpdate` 中执行，因为它与 Rigidbody 物理相关。

输入读取可以放在 `Update` 中，再将结果缓存给物理逻辑使用。

## 17. 调参原则

本项目的飞行手感高度依赖数值调节。

以下参数应尽量暴露到 Inspector：

```txt id="1g7vqs"
activeLiftMultiplier
windPushMultiplier
windLiftMultiplier
turnMultiplier
wingTiltTurnMultiplier
staminaCostMultiplier
staminaRecoverSpeed
maxStamina
cellSize
defaultWindProbeRadius
```

不要把关键飞行参数硬编码在方法内部。

临时项目中，能在 Inspector 里调出手感，比写出漂亮但难改的公式更重要。

## 18. Agent 实现注意事项

Agent 实现本项目相关功能时，应遵循以下原则：

```txt id="e09a80"
优先简单、稳定、可调参
优先使用 Rigidbody 基础功能
优先使用 AddForce 施加中心力
谨慎使用 AddTorque，只用于简单姿态或转向控制
避免偏心力和复杂关节
避免复杂空气动力学模拟
避免把 VR 输入直接写死进飞行控制器
避免把风写成单一全局常量
```

如果需要新建脚本，应说明脚本挂载位置、Inspector 字段配置方式和测试方法。

如果需要修改风场或飞行公式，应说明改动会影响哪些核心数值。

## 19. 当前阶段最小可行目标

当前阶段最小可行版本应优先完成：

```txt id="v5qbl9"
1. 玩家鸟对象拥有 Rigidbody
2. 可以读取模拟输入，得到左右翼挥动速度、左右翼倾角、翼展
3. 玩家向下拍翼时获得主动升力
4. 场景中可以放置多个 WindProbe
5. WindFieldManager 可以通过空间哈希查询当前位置综合风
6. 玩家在风场中受到沿风向推动力
7. 玩家展开双翼时受到额外风升力
8. 可以通过 Gizmos 或 UI 观察关键调试数值
```

不要一开始就追求完整 VR、完整动画、完整关卡或完整鸟类空气动力学。

## 21. 项目核心判断标准

当 Agent 不确定某个实现是否合适时，应使用以下标准判断：

```txt id="u675jj"
它是否能让鸟飞起来？
它是否方便调参？
它是否保持物理可控？
它是否保留未来 VR 输入替换空间？
它是否能清晰观察风和翅膀输入数值？
它是否避免了不必要的复杂架构？
```

如果答案大多为是，就倾向于采用。

如果一个方案非常真实但难以调试、难以理解、容易物理炸飞玩家，则不适合当前阶段。
